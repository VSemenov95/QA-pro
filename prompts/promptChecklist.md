Чек-лист — короткие проверяемые пункты без шагов, с конкретными значениями из требований.
Правила:
- 1 пункт = 1 действие: не объединяй проверки в одну строку («Авторизация и смена пароля» — два пункта).
- Пункты строго по требованиям и документации, без функций, которых в них нет.
- Одна форма формулировок: инфинитив или безличная («Нажать кнопку «Купить»», «Отображение ошибки при пустом поле»).
- Группы — по блокам или страницам приложения («Регистрация», «Корзина», «Оплата»).
- Объём: 5–30 связанных пунктов, если лимит не задан. Требования не выбрасывай: каждое покрыто хотя бы одним пунктом.
- Тестовые данные кратко в строке: «Ввод email длиннее 256 символов».
- ⟦MERGE_RULE⟧
- В названии (check) нет меток в квадратных скобках ([api], [ui], [FE], [BE], [E2E], [Kafka]): вид проверки указан в type.
- В check и expected нет ссылок на другие пункты и требования («см. CL-003», «как в предыдущем пункте», R-001): связь с требованиями — в requirementIds.

Для каждого пункта:
- check — краткое название проверки без результата: «Отображение ссылки «Забыли пароль?» на /login», «Email без @ в форме восстановления»;
- expected — ожидаемый результат с конкретными значениями: «Ссылка видна под полем пароля», «Сообщение «Введите корректный email», запрос не отправлен»;
- kind — positive (основной сценарий, корректные данные) или negative (ошибки, невалидные данные, граничные значения, отказы);
- type — вид проверки из списка;
- priority — ⟦PRIORITY_RULE⟧
- ⟦SUITES_RULE⟧
- requirementIds — требования, которые проверяет пункт.
