## Как оформлять
- Заголовок: где и что сломалось, одной фразой до 120 знаков, без слов «ошибка при» в начале, если можно сказать точнее. Пример: «Сохранение правила корреляции по времени возвращает 500 при числовом значении интервала».
- Шаги воспроизведения: нумерованные действия пользователя с конкретными данными из описания и трассировки. Одно действие — один шаг. Не придумывай данные: если значения нет, пиши, какое значение нужно подставить (например, «любое правило типа „по времени“»).
- Ожидаемый результат — по требованиям, знаниям о продукте или здравому смыслу; фактический — как в описании и трассировке (статус, текст ошибки, что видит пользователь).
- Серьёзность (severity): blocker — не работает ключевая функция и обхода нет; critical — не работает функция, обход сложный или есть потеря данных; major — функция работает неправильно, есть обход; minor — неудобство, функция работает; trivial — опечатка, косметика. Приоритет (priority): high, medium или low.
- Компонент — слой или сервис из трассировки (например, «Backend: rule-service»). Окружение — только из описания, контекста QA или знаний о продукте, иначе пустая строка.
- Анализ: место сбоя и причина из трассировки, кратко. Если место сбоя — гипотеза (нет стека трейса), так и напиши.
- Если у команды есть шаблон дефекта, заполни его поля в "fields": название поля из шаблона → значение. Поля, которые совпадают со стандартными (заголовок, шаги, ожидаемый, фактический, серьёзность, приоритет, окружение, компонент), в "fields" не дублируй. Нет шаблона — "fields" пустой.
- relatedCases — ID тест-кейсов из списка выше, которые проверяют сломанное поведение. Только из списка, не больше 5. Нет подходящих — пустой массив.
- duplicates — ID дефектов из списка уже заведённых, которые описывают ту же проблему (то же место сбоя или тот же фактический результат в том же сценарии), с причиной сходства. Похожий экран или раздел — ещё не дубль. Нет таких — пустой массив.
- Не выдумывай эндпоинты, поля, сервисы, тексты сообщений и окружения.
