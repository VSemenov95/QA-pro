## Как оформлять
- Заголовок: где и что сломалось, одной фразой до 120 знаков, без «ошибка при» в начале, если можно точнее. Пример: «Сохранение правила корреляции по времени возвращает 500 при числовом значении интервала».
- Шаги: нумерованные действия пользователя с данными из описания и трассировки; одно действие — один шаг. Не придумывай данные: если значения нет, напиши, что подставить (например, «любое правило типа „по времени“»).
- Ожидаемый результат — по требованиям, знаниям о продукте или здравому смыслу; фактический — как в описании и трассировке (статус, текст ошибки, что видит пользователь).
- severity: blocker — ключевая функция не работает и обхода нет; critical — функция не работает, обход сложный или есть потеря данных; major — работает неправильно, есть обход; minor — неудобство, функция работает; trivial — опечатка, косметика. priority: high, medium или low.
- component — слой или сервис из трассировки (например, «Backend: rule-service»). environment — только из описания, контекста QA или знаний о продукте, иначе пустая строка.
- analysis — место сбоя и причина из трассировки, кратко. Если место сбоя — гипотеза (нет стека), так и напиши.
- Если у команды есть шаблон дефекта, заполни его поля в "fields": название поля из шаблона → значение. Стандартные поля (заголовок, шаги, ожидаемый, фактический, серьёзность, приоритет, окружение, компонент) в "fields" не дублируй. Нет шаблона — "fields" пустой.
- relatedCases — ID кейсов из списка выше, которые проверяют сломанное поведение. Только из списка, не больше 5; нет подходящих — пустой массив.
- duplicates — ID уже заведённых дефектов, которые описывают ту же проблему (то же место сбоя или тот же фактический результат в том же сценарии), с причиной сходства. Похожий экран или раздел — не дубль; нет таких — пустой массив.
- Не выдумывай эндпоинты, поля, сервисы, тексты сообщений и окружения.
