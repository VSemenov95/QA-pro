QA pro: план доработок

Пять доработок, которые снимают с тестировщика ручную работу до генерации кейсов и после неё. По каждой: зачем она, как работает, что увидит пользователь, что нужно для реализации и чем рискуем. Скрины — макеты на настоящем интерфейсе QA pro, данные в них примерные.

Предложение 1

Дефект из трассировки — в Сфера.Задачи

Сложность средняяСрок 1–1,5 неделиГде режим «Трассировка»Статус оформление готово, в ветке

Что уже сделано

В ветке feature/defect-report агент оформляет баг-репорт по трассировке и шаблону команды, подбирает связанные кейсы, ищет дубли среди дефектов продукта. Дефект можно скопировать или скачать. Не хватает главного: завести его в трекер.

Как будет работать

  1. Завести в Сфера.Задачи. Под карточкой — проект, тип задачи «Дефект», исполнитель, спринт или релиз. Проект и исполнитель подставляются по компоненту из трассировки, команда может задать соответствие в настройках.
  2. Поля. Стандартные поля и поля шаблона команды раскладываются по полям задачи Сферы. «Предпросмотр полей Сферы» показывает, что куда попадёт.
  3. Связи. К задаче привязываются тест-кейс и требование, стек трейса — вложением, похожий дефект — связью «дубликат / связана».
  4. Дубли — по самой Сфере. Перед созданием агент ищет похожие задачи в проекте Сферы, а не только среди сохранённых в QA pro. Если похожий дефект уже исправлен — предлагает его переоткрыть вместо нового.
  5. Обратная связь. Номер задачи (RECOV-326) и её статус из Сферы показываются в карточке и в списке «Дефекты продукта». Исправленные дефекты потом используются в регрессе (предложение 3).

Что нужно для реализации

  • Загрузчик Сферы: новые операции для Сфера.Задачи — поиск задач, чтение полей проекта, создание задачи, вложение, связи, чтение статуса. Работают под входом пользователя в Сферу, как сейчас загрузка кейсов.
  • Мост: те же операции для QA pro в приложении Claude — по уже работающему каналу «мост ↔ загрузчик».
  • Соответствие полей: вкладка «Шаблон дефекта» получает раздел «Поля Сферы»: поле шаблона → поле задачи, значения серьёзности и приоритета.

Риски

API Сфера.Задачи не изучен

Загрузчик сейчас вызывает только API тестирования (/app/testing/api/v1). Первый шаг — записать запросы Сферы при ручном создании дефекта (HAR из DevTools) и по ним описать операции. Обязательные поля у проектов разные — их нужно читать из Сферы, а не зашивать.

Предложение 2

Каркас автотестов из тест-кейсов

Сложность высокаяСрок 3–4 неделиГде новая вкладка «Автотесты»

Зачем

Ручной кейс в автотест переписывают руками: те же шаги, тот же ожидаемый результат, но в коде. На это уходит больше времени, чем на сам кейс. Если генерировать код без знания проекта, получится тест, который придётся переписывать: другие клиенты, другие аннотации, дубли уже написанных методов.

Поэтому главное в этой доработке — анализ существующего проекта автотестов. Агент пишет тест так, как его написал бы человек из команды, и берёт готовое, а не пишет заново.

Как работает

  1. Подключить проект — один из трёх источников, проект привязывается к продукту:
    • Локальный репозиторий. Папка на компьютере тестировщика. Мост приложения Claude читает файлы с диска; в автономной версии в Chrome — выбор папки в браузере. Подходит, когда тесты ещё не запушены или репозиторий во внутреннем GitLab.
    • Репозиторий в Сфере. Загрузчик Сферы в Chrome становится ещё и импортером: под входом пользователя в Сферу читает дерево и файлы репозитория выбранной ветки и передаёт их в QA pro через мост — тем же каналом, которым сейчас уходят кейсы в обратную сторону.
    • Архив .zip — запасной путь без моста и загрузчика.
  2. Анализ проекта. Агент читает сборку, базовые классы, клиенты, модели, Page Object, хелперы, 10–20 типичных тестов и составляет профиль проекта: стек, структуру, стиль команды, каталог того, что можно переиспользовать.
  3. Генерация. Выбираете кейсы — агент пишет тесты по профилю. Для каждого шага сначала ищет готовый метод в каталоге, новое добавляет только когда подходящего нет, и делает его по образцу соседних.
  4. Проверка. Код компилируется на копии проекта (мост запускает gradle compileTestJava). Ошибки компиляции агент исправляет сам, до трёх попыток.
  5. Выдача. Для репозитория в Сфере — ветка и запрос на слияние в Сфере через загрузчик. Для локальной папки — файлы записываются в рабочую копию, коммит и пуш делает тестировщик. Также архив или копирование. В описании — ссылки на кейсы и требования.

Что входит в анализ проекта

  • Стек и сборка: Gradle или Maven, JUnit 4/5 или TestNG, RestAssured, Selenide, Allure, Owner, Lombok, AssertJ.
  • Структура: где лежат тесты, клиенты, модели, страницы; как называются классы и методы.
  • Стиль: аннотации, оформление шагов, проверки, работа с тестовыми данными и учётками, как подключается конфиг и стенд.
  • Каталог переиспользования: сигнатуры публичных методов с коротким описанием — по нему агент ищет готовое для каждого шага.
  • Обновление: профиль пересобирается по кнопке или при изменении основной ветки; меняются только затронутые части.

Что нужно для реализации

  • Загрузчик Сферы → импортер: операции чтения репозитория (ветки, дерево, файлы) и создания ветки и запроса на слияние в Сфере, под входом пользователя. В мосту — новый тип задания «импорт», результат возвращается порциями: большой проект не пролезет одним сообщением.
  • Локальная папка: инструменты моста project_list, project_read, project_write только внутри папки, выбранной пользователем. В Chrome-версии — File System Access API.
  • Промпты анализа проекта и генерации кода, хранение профиля в продукте.
  • Компиляция — инструмент моста compile на локальной копии (для репозитория из Сферы мост держит её во временной папке). Без моста — только архив и копирование.
  • Начать стоит с API-тестов: у них лучше всего видно переиспользование клиентов и моделей. UI и E2E — вторым шагом.
Риски

Большой проект не влезет в контекст целиком — нужен каталог сигнатур вместо исходников. Компиляция требует JDK на компьютере. API репозиториев Сферы, как и Сфера.Задачи, нужно сначала изучить по запросам самой Сферы. Сейчас проект для обкатки не выбран: функциональность закладывается под любой Java-проект.

Предложение 3

Регресс к релизу

Сложность средняяСрок 2–3 неделиГде новый режим «Регресс»

Зачем

Перед релизом QA-лид отбирает регресс руками: читает документацию новой функциональности и список исправленных дефектов, вспоминает, какие кейсы что проверяют, и выбирает на глаз. Прогнать всё — долго, выбрать мало — пропустить поломку. Особенно опасны исправления: правка в общем сервисе или валидаторе ломает соседнюю функциональность, о которой в задаче ни слова.

Как работает

  1. Документация новой функциональности. Загружаете документы релиза. Новая версия существующего ТЗ сравнивается с прошлой версией в продукте; новый документ разбирается целиком как новая функциональность.
  2. Исправленные дефекты. Добавляете дефекты релиза: из Сфера.Задачи по фильтру (релиз, статус «Исправлен»), по номерам или вручную. Агент читает описание, комментарии и, если есть, трассировку из QA pro.
  3. Анализ влияния. Для каждого изменения и каждого исправления агент определяет, какую функциональность оно могло задеть: напрямую (то же требование) и косвенно — через общие экраны, эндпоинты, сервисы и бизнес-правила из паспорта продукта и знаний о месте сбоя. Каждая связь — с объяснением.
  4. Решение по каждому кейсу продукта: «обязательно» (перепроверка исправления, затронутое требование, смоук), «рекомендуется» (косвенное влияние) или «пропустить» — с причиной. Учитывает приоритет и бюджет времени.
  5. Пробелы: новая функциональность и исправления без единого кейса — с кнопкой «Сгенерировать кейсы». Устаревшие кейсы — с переходом в актуализацию.
  6. Выдача: тест-план в Сфере через загрузчик или .xlsx.

Что нужно для реализации

  • Сравнение версий документа: текстовый дифф по разделам, затем модель описывает смысл изменений. Новые документы проходят обычный анализ требований.
  • Дефекты из Сфера.Задачи — через те же операции загрузчика, что и в предложении 1; дефекты, заведённые из QA pro, уже несут трассировку и место сбоя — по ним влияние определяется точнее.
  • Связи «требование → кейсы» уже есть в продукте; зависимости между требованиями и общие сервисы берутся из паспорта.
  • Оценка времени — по числу шагов кейса и истории прогонов, если она появится в Сфере.
  • Создание тест-плана в Сфере — новый вызов загрузчика.

Риски

Точность связей

Косвенное влияние агент выводит из паспорта продукта: чем он подробнее (сервисы, общие компоненты), тем точнее выбор. По дефекту без места сбоя влияние — гипотеза, такие строки помечены. Решение «пропустить» опирается на ссылки кейсов на требования. Кейсы без ссылок (импорт из старой ТМС) агент сопоставит по тексту, но такой выбор помечается «проверьте». Пропущенные кейсы видны в списке — QA-лид может вернуть любой одним нажатием.

Предложение 5

Ревью ТЗ для аналитика

Сложность низкаяСрок 1 неделяГде вкладка «Ревью ТЗ» в запуске

Зачем

Ошибка в требовании, найденная до разработки, стоит один вопрос аналитику. Та же ошибка после релиза — дефект, исправление, перепроверка. Сейчас вопросы QA pro собирает внутри запуска, но они нужны генерации, а не аналитику: их нельзя отправить одним письмом, у них нет цитаты из документа и предложенной формулировки.

Как работает

  1. Запускается отдельно, до генерации, или вместе с ней — на тех же документах.
  2. Агент проверяет каждое требование по пяти видам проблем: неоднозначность («быстро», «удобно»), противоречие между разделами, нет значения (текста ошибки, лимита, срока), нет негативного сценария, нетестируемое требование.
  3. По каждой находке: цитата с номером раздела, почему это проблема, какие кейсы от неё зависят, вопрос аналитику и предложенная формулировка.
  4. Тестировщик отбирает находки: «в вопросы аналитику», «принять формулировку» или «не проблема». Последнее агент запоминает как правило команды.
  5. Выдача: текст письма, комментарии к требованиям в Сфере или .docx. Ответы попадают в знания о продукте, а затронутые кейсы агент правит сам — этот механизм уже работает.

Что нужно для реализации

  • Новый промпт ревью требований поверх уже готового анализа: документы второй раз не читаются целиком.
  • Вкладка, фильтры и статусы находок — по образцу вкладки «Ревью».
  • Связь с «Вопросами» и знаниями о продукте уже есть.

Риски

Шум

Агент может придираться к формулировкам, которые команде понятны. Отсекается порогом важности (мелочи свёрнуты) и памятью: «не проблема» становится правилом, и такие находки больше не появляются.

Предложение 6

Матрица покрытия

Сложность низкаяСрок 3–5 днейГде вкладка «Покрытие»

Зачем

Трассировка «требование → кейсы» есть только внутри JSON-экспорта. На демо, в отчёте о тестировании и при планировании нужна наглядная таблица: какие требования покрыты, каким видом тестов, где пробелы.

Как работает

  1. Строки — требования запуска или всего продукта, столбцы — API, UI, E2E и смоук. В ячейке — число кейсов.
  2. Цвет ячейки: зелёный — покрыто, красный — пробел. «—» — этот вид тестов к требованию не относится (по плану тестирования).
  3. Фильтры: пробелы, без смоука, поиск. Сверху — процент покрытия.
  4. По пробелу — кнопка «Покрыть требование»: функция уже есть, матрица просто ведёт к ней. Или «Исключить из покрытия» с причиной.
  5. Выгрузка .xlsx для отчёта.
Дешевле всего из четырёх

Все данные уже есть: требования, связи кейсов, план по видам тестов, покрытие отдельного требования. Новых запросов к модели нет — только интерфейс и выгрузка.
