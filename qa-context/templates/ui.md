# Шаблон UI

idPrefix: UI-

## Правила

- Шаги пишутся с точки зрения пользователя: что открыть, куда нажать, что ввести.
- Названия элементов — как в интерфейсе, в кавычках-ёлочках: кнопка «Отправить».
- У каждого шага есть ожидаемый результат, который видно на экране.
- Валидации полей: отдельный кейс на каждый класс эквивалентности и границу.
- priority: P3_HIGH — основной пользовательский путь, P2_MEDIUM — валидации и сообщения, P1_LOW — косметика и редкие случаи, P4_CRITICAL — блокирует работу или безопасность. Других значений нет.
- Не добавляй кейсы на косметику и повторы: визуальное различие состояний чекбокса, текст подсказки, невозможность перетаскивания пунктов, метки, если они не входят в требования.
- Проверяй тоглы включения и отключения метрик и добавление метрики отдельными шагами: тоглы неактивны, добавление невозможно.
- Для запрета редактирования пиши ожидаемый результат коротко: «Редактирование невозможно», «Тогл задизейблен» или «Добавление невозможно». Без цитат подсказок.
- Пиши название по шаблону «[FE] <область>: <проверяемое поведение при условии>», одинаковым для всех кейсов; один кейс — одна проверяемая настройка.
- Предусловия пиши короткими отдельными пунктами: данные, версия с нужной настройкой, роль и назначение, авторизация; без пересказа настройки целиком.
- Начинай шаги с навигации по меню одной строкой через «->», затем объединяй близкие действия одного экрана в один шаг через «И».
- Ожидаемый результат о запрете пиши коротко («Редактирование невозможно», «Тогл задизейблен»); не цитируй подсказки и не повторяй описание шага.
- Задавай конкретные значения полей в шаге списком «Поле = значение»; значения из предусловия обозначай ссылкой вида {ШК из предусловия}.
- Для типовых кейсов одного вида формулируй шаги одинаково: те же глаголы («Перейти», «Открыть», «Нажать», «Заполнить») и те же названия элементов.
- Указывай в шаге одно проверяемое действие над одним элементом и сразу его ожидаемый результат; не объединяй проверки разных элементов в один шаг.
- Начинай название кейса с метки «[FE]», затем область и проверяемое поведение; называй тестируемое условие одной короткой фразой без пояснений и без перечисления в конце.
- Заполняй поля формы списком «Поле = значение» и ссылайся на данные из предусловия через {…из предусловия}; не придумывай новые имена данных внутри шага.
- Расставляй приоритет по значимости проверки; для основных проверок блокировки и доступа используй высокий приоритет, для вспомогательных — средний, косметике низкий не присваивай отдельные кейсы.
- Начинай шаги глаголом в неопределённой форме («Перейти», «Открыть», «Нажать», «Заполнить») и соединяй навигацию с действием на одном экране через «И» на отдельной строке.

## Образец

```json
{
  "id": "UI-001",
  "title": "[FE] Восстановление пароля: ошибка при email без символа @",
  "priority": "P2_MEDIUM",
  "preconditions": [
    "Открыта страница /login",
    "Пользователь не авторизован"
  ],
  "steps": [
    {
      "step": 1,
      "action": "Нажать ссылку «Забыли пароль?»",
      "expected": "Открыт экран «Восстановление пароля» с полем Email и кнопкой «Отправить ссылку»"
    },
    {
      "step": 2,
      "action": "Ввести в поле Email значение userexample.ru",
      "expected": "Значение отображается в поле"
    },
    {
      "step": 3,
      "action": "Нажать «Отправить ссылку»",
      "expected": "Под полем сообщение «Введите корректный email», запрос на сервер не отправлен"
    }
  ],
  "expectedResult": "Форма не отправляется, пользователь видит подсказку об ошибке формата",
  "tags": [
    "negative",
    "validation"
  ]
}
```
