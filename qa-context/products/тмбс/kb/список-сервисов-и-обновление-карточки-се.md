# Список Сервисов и обновление карточки Сервиса: UI, пермиссии и API-контракты

> Реализация отображения списка Сервисов и обновления карточки Сервиса на UI: новые таблицы, эндпоинты, пермиссии PPBP_SERVICE_READ и PPBP_SERVICE_UPDATE.

### Описание
- Документ предназначен для описания технического решения по фиче «Передача метрик из ТМБС в ЗСМ в привязке к сервисам с агрегирующим расчетом на стороне ТМБС».
- Бизнес-требования: «ТМ. Просмотр списка сервисов», «Обновление карточки Сервиса».
- User Story: «ТМ. Просмотр списка сервисов».
- Связанные техрешения: «Сфера.Конфигурации» — текущее интеграционное решение с системой Сфера.Конфигурации; «Сервис - Пермиссии для Сервисов»; «ТМ. [СА] Принадлежность метрик БС, выч. атрибутов и КТ к Сервису» — техническое решение в рамках привязки метрик БС, выч. атрибутов, КТ к Сервису.

### Экраны и навигация
- Страница «Сервисы» — процесс отображения списка Сервисов (диаграмма «Список Сервисов»).
- Страница «Карточка Сервиса» — процесс обновления «Карточки Сервиса» (диаграмма «Карточка Сервиса»).

### Бизнес-правила и ограничения
- Необходимо реализовать новые таблицы service, s_system_inf_system, s_system_bs_system, включая механизмы, предусмотренные в п. 4.1.
- Реализовать механизмы, описанные на сиквенс-диаграммах «Список Сервисов» и «Карточка Сервиса».

### API и интеграции
- GET /api/service/header — получение параметров списка Сервисов (новый эндпоинт).
- POST /api/service/update-config/{serviceId} — запрос на обновление конфигурации карточки Сервиса (обновляется конфигурация метрик Сервиса).
- Для обоих контрактов в документе указан статус «Новый».
- Для GET /api/service/header: создание пермиссии PPBP_SERVICE_READ для доступа к списку Сервисов; проверки пермиссии PPBP_SERVICE_READ на стороне BE.
- Для эндпоинта обновления: создание пермиссии PPBP_SERVICE_UPDATE для осуществления процесса обновления конфигураций метрик Сервиса; проверки пермиссии PPBP_SERVICE_READ на стороне BE и FE (так указано в документе). В тексте п. 4.2 второй новый эндпоинт указан как «GET /api/service/header» (по-видимому, опечатка; в таблице API-контрактов — POST /api/service/update-config/{serviceId}).

### Роли и права
- PPBP_SERVICE_READ — доступ к списку Сервисов.
- PPBP_SERVICE_UPDATE — обновление конфигураций метрик Сервиса.

### Поля и элементы
**Модель данных (все со статусом «Новый»):**
- service — создание новой таблицы для хранения объектов новой сущности «Сервисы».
- s_system_inf_system — создание новой таблицы для хранения связей между объектами сущностей «Информационные системы» и «Сервисы».
- s_system_bs_system — создание новой таблицы для хранения связей между объектами сущностей «Бизнес-сервисы» и «Сервисы».

### Поля и элементы
- Таблица «Список сервисов» включает атрибуты из п. 13.1 (таблица ниже).
- Элементы пагинации: селект фильтрации по записям таблицы «Записей на странице» (возможные значения: 10, 20, 50); элемент текущего отображения записей в таблице; селект пагинации по страницам; кнопка «Вперед»; кнопка «Назад».
- Форма «Поиск»: плейсхолдер «Поиск по ID, коду, Сервису, Бизнес Сервису»; элемент «крестик» для сброса.
- Таблица атрибутов (13.1): все атрибуты обязательные («Да»), Default — «-».
  1. id — «ID», int32, макс. длина: по ширине колонки.
  2. code — «Код», string, по ширине колонки.
  3. name — «Название Сервиса», string, по ширине колонки.
  4. extServiceId — «ID Внешний», string, по ширине колонки.
  5. businessServices.name — «Бизнес Сервисы», string; 20 символов для наименования БС в чипсе; вывод двух значений чипсы в строке; в случае если БС более 2-ух — отображать count чипс с числовым значением скрытых БС.
- Правила валидации (13.2) и поиск и фильтрация (13.3): не заданы (прочерки).

- КП 3.2 (неудача): выполнен КП 3.0; пользователь вводит значение; система НЕ находит значения, отображает пустой список по Сервисам и плейсхолдер в списке Сервисов. Тест-кейсы: PPBP-1109, PPBP-1110.

Тест-кейсы: PPBP-1115, PPBP-1117.

### API и интеграции
- Запрос списка сервисов: ошибки 400, 404, 500, 403 либо 200 Ок без данных в теле ответа приводят к отображению страницы «Сервисы» с пустым списком (КП 1.2, 2.2).
- Ролевая модель должна быть применена для UI и API.

### Сообщения и ошибки
- Плейсхолдер формы «Поиск»: «Поиск по ID, коду, Сервису, Бизнес Сервису».
- Плейсхолдер в списке Сервисов при ненайденных значениях: «Ничего не найдено. Уточните поисковый запрос».
- Ошибки запроса списка: 400, 404, 500, 403; при них (и при 200 Ок без данных) отображается пустой список.
- Макеты форм с ошибками 400, 500, 404, 403 есть в Пиксо; по решению встречи 12.03.2026 эти экраны будут реализованы после основного функционала (КП 1.0–5.0), при наличии капасити — в рамках единого обработчика ошибок. Группе QA учитывать при тест-дизайне.

### Роли и права
- Пользователь авторизован в соответствии со «Список ролей системы».
- Роль: Администратор (в критериях — «Роль 1»).
- Разрешение: PPBP_SERVICE_READ (в критериях — «Разрешение 1»), ID не указан; выдаётся в соответствии с документом «Сервис».

### Сценарии
- Открыть страницу «Сервисы» с Главной через «Быстрые ссылки» (КП 1.0, 1.1, 1.2).
- Открыть страницу «Сервисы» из верхнего меню (КП 2.0, 2.1, 2.2).

- Наведение на count чипс для просмотра скрытых БС (КП 5.0).
