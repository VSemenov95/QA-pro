# Повторная отправка события мониторинга (trmonbs_metrics_retry)

> Механизм гарантированной повторной отправки событий мониторинга ТМБС в REST API зонтичной системы мониторинга (ЗСМ) через Kafka-топик trmonbs_metrics_retry сервисом trmon-ecm-integration-service.

### Описание
- Пользовательская история: «Я как Администратор системы хочу иметь возможность гарантированно отправить событие мониторинга для того, чтобы все события мониторинга были обработаны, доставлены до конечного адресата, чтобы ко мне не было претензий об отсутствии оповещений по проблемам». (7-Повторная отправка события мониторинга)
- Причина: сценарии отказа («Формирование сценариев отказоустойчивости»): если API ЗСМ недоступно, события ТМБС нужно доставить позже, т.к. они выявляют неисправности бизнес-сервисов. События должны быть гарантированно доставлены; при недоступности ЗСМ — переотправка. (7-Повторная отправка события мониторинга)
- Решение: повторная отправка в REST API ЗСМ при ошибках через топик trmonbs_metrics_retry, с управлением очередью и предотвращением коллизий между триггерами. Реализуется для trmon-ecm-integration-service. (7-Повторная отправка события мониторинга)
- История: 2025-05-13, Климов Александр, PPBP-823 [Analytics] «Подготовить спецификацию реализации повторной отправки событий мониторинга». (7-Повторная отправка события мониторинга)
- Отправка отклонений во внешнюю систему (E2E № 1) использует REST/KAFKA через ppbp-ecm-integration-service; метод задаётся FEATURE_PPPM_EVENTS_INTEGRATION_METHOD: KAFKA или REST (POST /listener-tbpm-s-rest-v1/alert, [Интеграция ТМБС-ЗСМ]). (ТМ. [СА] Настройка отклонений актуальная-29)

### Экраны и навигация
- Пользовательских интерфейсов нет. (7-Повторная отправка события мониторинга)

### Поля и элементы
- TM_MONITORINGEVENT_RETRY_BATCH_SIZE (retry.batch.size) = 50 — сообщений за одну попытку. (7-Повторная отправка события мониторинга)
- TM_MONITORINGEVENT_RETRY_INTERVAL_MS (retry.interval.ms) = 300000 — 5 минут между попытками, отсчёт с момента последней ошибки. (7-Повторная отправка события мониторинга)
- Топики: trmonbs_metrics — хранение событий для отправки в API ЗСМ; trmonbs_metrics_retry — для повторной отправки: TTL 30 минут, порядок FIFO, сообщения не теряются до истечения TTL. (7-Повторная отправка события мониторинга)

### Бизнес-правила и ограничения
- Параметры задаются переменными при выкатке микросервиса; пользователь не может менять их через интерфейс; переотправка прозрачна для пользователя. (7-Повторная отправка события мониторинга)
- Переотправка пачками, чтобы не было «лавины» событий. (7-Повторная отправка события мониторинга)
- Статус ответа != 200 — сообщение сохраняется в trmonbs_metrics_retry. (7-Повторная отправка события мониторинга)
- Триггер 1: после 200 OK новое сообщение — чтение до retry.batch.size сообщений из retry-топика и отправка. Триггер 2: по истечении retry.interval.ms с последней ошибки — чтение retry.batch.size и отправка. (7-Повторная отправка события мониторинга)
- Если хотя бы одно сообщение батча не отправлено (!= 200), весь батч возвращается в trmonbs_metrics_retry (перезапись с новым TTL = 30 мин, не копирование, порядок сохраняется); фиксируется ошибка; таймер запускается (если не запущен) и сбрасывается — отсчёт retry.interval.ms заново. (7-Повторная отправка события мониторинга)
- Следующая отправка — через retry.interval.ms (если нет успешных отправок) или после следующего успешного сообщения. (7-Повторная отправка события мониторинга)
- Kafka автоматически удаляет сообщения через 30 минут (TTL). (7-Повторная отправка события мониторинга)
- Параллельные триггеры не должны вызывать повторную обработку одного сообщения. (7-Повторная отправка события мониторинга)
- Отклонения: после получения из внутренней KAFKA DTO обогащается из переменных: application (TM_MONITORINGEVENT_APPLICATIONNAME), metricKey, customAttributes.ppbpInstanceId (CONFIG_PPPM_DEVIATION_MESSAGE_INSTANCEID); валидация размера по CONFIG_PPPM_DEVIATION_MESSAGE_MAX_SIZE_IN_KB: превышение — ошибка в логи и прерывание. (ТМ. [СА] Настройка отклонений актуальная-29)

### API и интеграции
- Основной поток: чтение из trmonbs_metrics → отправка в REST API ЗСМ → при статусе != 200 запись в trmonbs_metrics_retry. (7-Повторная отправка события мониторинга)
- Отклонения отправляются в KAFKA для ppbp-ecm-integration-service, который валидирует и отправляет сообщения в сторонние системы. (ТМ. [СА] Настройка отклонений актуальная-29)

### Сообщения и ошибки
- Журнал при неуспешной повторной отправке: "Retry failed for batch. Status: {}. Retrying in {} ms" (status, retry.interval.ms). (7-Повторная отправка события мониторинга)
- Фиксируются HTTP 4xx, 5xx, сетевые сбои, таймауты. (7-Повторная отправка события мониторинга)

### Роли и права
- Администратор системы; параметры через интерфейс не меняются. (7-Повторная отправка события мониторинга)

### Сценарии
- Критерии приёмки: ответ != 200 (2XX) → сообщение в trmonbs_metrics_retry; интервальные попытки каждые retry.interval.ms, при неудаче сообщения остаются, TTL сбрасывается до 30 минут; ответ 200 → триггер успешной отправки; после неудачи отсчёт интервала заново; параллельные триггеры не дублируют обработку; через 30 минут сообщения удаляются. (7-Повторная отправка события мониторинга)
- Тесты: эмуляция 500 → сообщение в retry-топике; 200 OK → чтение и отправка retry.batch.size сообщений; недоступность API + ожидание retry.interval.ms → отправка по таймеру; TTL: через 30 минут сообщение удалено (проверка может не удаться, если Kafka решит не удалять). (7-Повторная отправка события мониторинга)
- Пример: в топике [A, B, C, D], batch=2; A,B → 500 → порядок [C, D, A, B], таймер перезапущен; через 5 минут C,D → 200, затем A,B → 200. (7-Повторная отправка события мониторинга)

### Необходимые доработки
- Внедрить переменные повторной отправки; создать топик trmonbs_metrics_retry и добавить в проверки при создании топиков через API; реализовать логику отправки по триггеру успеха, по времени и при неуспешной отправке из retry-топика. (7-Повторная отправка события мониторинга)
