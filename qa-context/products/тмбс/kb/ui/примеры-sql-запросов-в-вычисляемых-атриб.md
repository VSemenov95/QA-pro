# Примеры SQL-запросов в вычисляемых атрибутах, метриках и событиях мониторинга

> Встроенные (захардкоженные) примеры SQL-запросов в интерфейсе создания вычисляемых атрибутов, метрик и событий мониторинга, которые пользователь может редактировать, стирать и восстанавливать как основу для собственного кода.

### Описание
- Пользовательская история (PPBP-1883): «Я как Пользователь системы. Хочу Увидеть примеры SQL запросов выч. атрибутов, метрик, событий мониторинга. Для того, чтобы Написать SQL запросы основываясь на примерах». Пользователь при создании вычисляемых атрибутов транзакций, метрик бизнес-сервиса, событий мониторинга не всегда понимает, что писать в SQL; проще увидеть пример и написать свой. (24-[US] Стандартные примеры SQL-запросов в вычисляемых атрибутах, метриках и событиях мониторинга)
- Бизнес-требования: (1) пользователь должен увидеть пример SQL-запроса вычисляемого атрибута \ метрики \ события мониторинга; (2) пример SQL для каждого создаваемого выч. атрибута \ метрики \ события мониторинга. Компонент: UI. (24-[US] Стандартные примеры SQL-запросов в вычисляемых атрибутах, метриках и событиях мониторинга)
- История изменений: версия 1, 2024-03-28, Климов Александр, PPBP-1883 (Выполнено), «Создание документа, описание БТ». (24-[US] Стандартные примеры SQL-запросов в вычисляемых атрибутах, метриках и событиях мониторинга)

### Бизнес-правила и ограничения
- Примеры «вшиваются» (хард-код) в UI; пользователь не может изменить предложенные запросы. Система должна хранить примеры; в FE-части сохранить запросы-примеры (п. 6.4). Пример может загружаться из переменной при деплое из k8s. (24-[US] Стандартные примеры SQL-запросов в вычисляемых атрибутах, метриках и событиях мониторинга)
- Каждый вновь создаваемый выч. атрибут, метрика, событие мониторинга содержит пример SQL-кода. Система не подменяет отредактированный пользователем запрос примером. После сохранения отображается сохранённый запрос, который UI запрашивает с BE (хранится в БД BE). (24-[US] Стандартные примеры SQL-запросов в вычисляемых атрибутах, метриках и событиях мониторинга)
- SQL метрик и событий мониторинга может не исполняться: в запросах явно прописан бизнес-сервис, который может быть отключен, не иметь данных или не существовать. (24-[US] Стандартные примеры SQL-запросов в вычисляемых атрибутах, метриках и событиях мониторинга)
- Пример события мониторинга подставляется для срабатывающего события; если событие по данному БС не нужно, нужно прописать код события, который не будет генерировать событие. (24-[US] Стандартные примеры SQL-запросов в вычисляемых атрибутах, метриках и событиях мониторинга)
- Обработка и отображение ошибок написания/исполнения SQL в истории не рассматриваются; логика валидации полей ввода SQL не меняется. (24-[US] Стандартные примеры SQL-запросов в вычисляемых атрибутах, метриках и событиях мониторинга)

### API и интеграции
- Пример SQL может загружаться из переменной при деплое из k8s; UI запрашивает сохранённый SQL с BE (БД BE). (24-[US] Стандартные примеры SQL-запросов в вычисляемых атрибутах, метриках и событиях мониторинга)
- Примеры для FE (п. 6.4): 6.4.1 Вычисляемые атрибуты («Общий» 6.4.1.1, «С ожиданием по времени» 6.4.1.2, «Полнота» 6.4.1.3); 6.4.2 Метрика; 6.4.3 Событие мониторинга. Разнесение запросов по заголовкам в PDF однозначно не восстанавливается. Все начинаются с комментария «-- произведите замену переменных отмеченных как ${}». Пять запросов 6.4.1 по порядку: (1) select sum(amount) from data where event_stage in ('${payment_1}', '${payment_2}') having count(distinct event_stage) filter(where event_stage in ('${payment_1}', '${payment_2}')) = 2; (2) select min(event_time) from data where event_stage in ('${payment_1}', '${payment_2}'); (3) select max(event_time) from data where event_stage in ('${payment_3}', '${payment_4}'); (4) select min(event_time) from data where event_stage in ('${payment_1}', '${payment_2}'); (5) select count(1) from data where event_stage in ('${payment_3}'). (24-[US] Стандартные примеры SQL-запросов в вычисляемых атрибутах, метриках и событиях мониторинга)
- Запрос 1 (метрика): select sipHash64(metric_id, metric_time) as metric_uuid, '${metric_id}' as metric_id, toStartOfMinute(transaction_time) as metric_time, 'Имя метрики' as metric_name, count(distinct transaction_uuid) as metric_value, '1m' as metric_period, last_value(transaction_uuid) as metric_object, count(distinct transaction_uuid) as metric_object_count, toDateTime(now(),'Europe/Moscow') as insert_timestamp from `default`.bs_${bs_table}_attribute_distributed ba where attribute_id = '${id}' and transaction_time >= now() - toIntervalMinute(600) and attribute_threshold_type = 'CRITICAL' group by metric_time. (24-[US] Стандартные примеры SQL-запросов в вычисляемых атрибутах, метриках и событиях мониторинга)
- Запрос 2 (событие мониторинга): CTE metrics (severity: metric_value > 0 → 'CRITICAL', иначе 'NORMAL'; metricName, metricValue, timeAlertCreated, object, originalData, additionalAttributes, insert_timestamp, metric_object из default.bs_${bs_table}_metric_distributed md where metric_id='${metric_id}' and md.insert_timestamp > now('Europe/Moscow') - toIntervalHour(1)) и monitoring_events (externalId из default.bs_${bs_table}_monitoring_event_distributed me where externalId!=''); итоговый select: 'TRmonBS' as application, 'Бизнес-сервис' as category, severity, '${bs_id}' as ciName, '${service_name}' as serviceName, '2099 Транзакционный мониторинг. \n' as title, '${metric_name}' || title as alertText, metricName, metricValue, timeAlertCreated, metric_object as object, metric_object as originalData, insert_timestamp, metrics.object as externalId from metrics left join monitoring_events on metrics.object = monitoring_events.externalId where metrics.object != monitoring_events.externalId and severity!='NORMAL'. (24-[US] Стандартные примеры SQL-запросов в вычисляемых атрибутах, метриках и событиях мониторинга)

### Сценарии
- Логика: пользователь приходит в UI, создаёт выч. атрибут \ метрику \ событие, видит пример SQL, пример хранится в системе и при каждом создании подставляется в поле(я) SQL, пользователь редактирует и сохраняет, затем видит сохранённый код. (24-[US] Стандартные примеры SQL-запросов в вычисляемых атрибутах, метриках и событиях мониторинга)
- Критерии приёмки (только положительный сценарий), «Общий» (1.1): 1.1.1 в «Правила вычисления» в «Код вычисляемого атрибута» виден пример; 1.1.2 «Стереть SQL запрос» — пустое поле; 1.1.3 «Отменить» — ранее стёртый запрос; 1.1.4 «Восстановить» — пустое поле; 1.1.5 «Вернуться к исходному состоянию» — пример; 1.1.6 после редактирования (дописал строки ИЛИ изменил существующие) — изменённый запрос; 1.1.7 «Отменить» — запрос до редактирования (пример). (24-[US] Стандартные примеры SQL-запросов в вычисляемых атрибутах, метриках и событиях мониторинга)
- «С ожиданием по времени» (1.2): 1.2.1 в левом и правом полях «Код» примеры. При изменении только левого поля действия выполняются в левом, правое всегда остаётся с примером: 1.2.2 стереть — левое пустое, правое пример; 1.2.3 «Отменить» — слева стёртый запрос, справа пример; 1.2.4 «Восстановить» — слева пусто, справа пример; 1.2.5 «Вернуться к исходному состоянию» — в обоих пример; 1.2.6 редактирование слева — слева изменённый, справа пример; 1.2.7 «Отменить» — в обоих пример. Случаи «правое изменяет, левое не изменяет» и «оба изменяет» — «Аналогично предыдущему». (24-[US] Стандартные примеры SQL-запросов в вычисляемых атрибутах, метриках и событиях мониторинга)
- «Полнота» (1.3): «Аналогично предыдущему». Метрика (2) и Событие мониторинга (3): аналогично п. 1.1. (24-[US] Стандартные примеры SQL-запросов в вычисляемых атрибутах, метриках и событиях мониторинга)
