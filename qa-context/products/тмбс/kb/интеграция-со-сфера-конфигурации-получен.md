# Интеграция со Сфера.Конфигурации: получение цепочек сервисов, сервисов и ИС

> Интеграция ТМБС со Сфера.Конфигурации для получения цепочек сервисов, сервисов и привязанных ИС (через REST и Kafka) и их сохранения в интеграционных и системных таблицах PG для последующей постановки на мониторинг.

### Описание
- История: «Я как Пользователь системы. Хочу Получать из Сфера.Конфигураций Цепочки Сервисов, Сервисы и привязанные к ним ИС. Для Дальнейшей постановки на мониторинг». Версия документа на 15.06.2026. (Акутальная Сфера.Конфигурации -5)
- Аксиомы: цепочка бизнес-сервисов — объект категории «Сервис» с 1+ сервисами, к каждому относится 1+ ИС; в системе приравнивается к «Бизнес-Сервису»; прочие объекты «Сервис» не мониторятся, хранятся для обогащения таблиц связей. (Акутальная Сфера.Конфигурации -5)

### Поля и элементы
- Kafka-сообщения (msgId, msgType, msgAction, attributes): цепочка — PPCM-CI/update, type.code bizservice_serviceChain_configItem, configItemType «Цепочка сервисов»; ИС — PPCM-CI/update, RIS_IS_configItem, configItemCategory «РИС», configItemType «ИС»; ИТ-сервис — bizservice_ITService_configItem, configItemCategory «Сервис»; связь — PPCM-LINK/create, type.code link, status {active, «Активна»}, relationType (id 5, PARENT, «Родительская КЕ», backType «Дочерняя КЕ»), innerEntityCI1, innerEntityCI2, CI1, CI2, sourceSystem «2078». (Акутальная Сфера.Конфигурации -5)
- Таблицы PG: новые интеграционные configuration_integration_is (ИС), _services (сервисы), _chains (цепочки), _link (связи); конечные business_services, int_configuration_services, information_system, bs_system_inf_system, datablock (связь технологов и владельцев с БС), datablock_data. (Акутальная Сфера.Конфигурации -5)
- configuration_integration_is: id serial4; external_id (PK)←number; name; code←itsLinkedSubsCode; description←itsDescription; create_date←createdDate; modify_date←updatedDate; version; details json. (Акутальная Сфера.Конфигурации -5)
- configuration_integration_services (PK external_id+version; конечная int_configuration_services): id, external_id←number, name, code←itServCode, type←itServType, status, criticality←itServCriticality, stream, description, created_date←createdDate, modify_date←updatedDate, version int4←itsVersion, relatedIs, details JSON. (Акутальная Сфера.Конфигурации -5)
- configuration_integration_chain (PK external_id+version; конечная business_services): те же поля, что у services, без relatedIs. (Акутальная Сфера.Конфигурации -5)
- configuration_integration_link: id, number (PK), name, CI1, CI2, external_id←chainId, details JSON. (Акутальная Сфера.Конфигурации -5)
- datablock_data: id, name (всегда «ФИО»), value (technologist, ctOwner), datablock_id int4, order int4. datablock: id, type (bs_technologist — из tehnologhist; bs_owner — из ctOwner), order, bs_id int4. (Акутальная Сфера.Конфигурации -5)

### Бизнес-правила и ограничения
- БТ 1: обновление по шедуллеру в админ-сервисе, 1 раз в сутки; обновляются только объекты со статусами из п. 5.1. (Акутальная Сфера.Конфигурации -5)
- БТ 2: цепочка наследует ИС сервисов внутри неё. БТ 3: существующие связи БС с ИС удалить нельзя, только дополнить. (Акутальная Сфера.Конфигурации -5)
- В datablock_data для каждого уникального Value — своя запись. (Акутальная Сфера.Конфигурации -5)

### API и интеграции
- Первичный забор: REST /api/v1/entities (PPCM. REST API, OAuth 2.0), однократное наполнение. Далее — топик Kafka 2078.ppcm-dataEvent-ke-output-1.0 (документ «PPCM: Kafka»). (Акутальная Сфера.Конфигурации -5)
- Фильтр (status «exploitation»): RIS_IS_configItem→configuration_integration_is→information_system; bizservice_ITService_configItem и bizservice_Service_configItem→configuration_integration_services→service; bizservice_serviceChain_configItem→configuration_integration_chains→business_services; Link (status.code «active»)→таблица связей→s_system_bs_system, s_system_inf_system, bs_system_inf_system. (Акутальная Сфера.Конфигурации -5)

### Сценарии
- Шаг 1 (первичное наполнение по REST): типы RIS_IS_configItem, bizservice_ITService_configItem, bizservice_Service_configItem, bizservice_serviceChain_configItem, Link загружаются вызовом /api/v1/entities в configuration_integration_services, _chains, _is, _link (с фильтрацией по п. 5.1). Затем без доп. фильтров: ITService и Service из _services в service; RIS_IS_configItem из _is в information_system; bizservice_Service_configItem (код как в документе) из _chains в business_services.
- Шаг 2 (обновление): ITService, Service, serviceChain из kafka в _services («Service», «ITService») и _chains («serviceChain»); RIS_IS_configItem в _is; Link в _link. Проверка по первичному ключу: нет — кладём, совпал — перезаписываем.
- Внутренние таблицы: п. 8: serviceChain из _chains в business_services, datablock, datablock_data. Ключа нет — перекладываем по маппингу 6.3.3, 6.3.5, 6.3.6. Ключ совпал: external_id из _chains сверяется с business_services, берётся id, в monitoring_card ищется bs_id = id. Карточка в DRAFT или записи в monitoring_card нет — обновляем по маппингу; карточка не в DRAFT — ничего не происходит. Диаграмма 1. п. 9: RIS_IS из _is в information_system; п. 10: ITService и Service из _services в service (нет — кладём, совпал — перезаписываем).
- П. 11 (связи): отдельная процедура при каждом обновлении интеграционного слоя; в _link пишутся связи БС -> Сервис и Сервис -> ИС; фильтр Link: "relationType" : {"relationKey": "PARENT"}; из _link в bs_system_inf_system, s_system_bs_system, s_system_inf_system. Тип по "innerEntityCI1.typeCode": bizservice_serviceChain_configItem — БС -> Сервис; bizservice_ITService_configItem или bizservice_Service_configItem — Сервис -> ИС; иные типы — процесс останавливается. CI2 ищется по external_id: для БС -> Сервис в service, запись в s_system_bs_system (bs_id из business_service, service_id из service); для Сервис -> ИС в information_system, запись в s_system_inf_system (inf_system_id, service_id). Нет соответствий — процесс завершается. bs_system_inf_system: по external_id = CI1 находим внутренний ID БС, в s_system_bs_system — service_id, в s_system_inf_system — inf_system_id; пишем inf_system_id и bs_id (в документе указано «из таблицы service»). Диаграмма 2.
- Статусная модель (6.3): active и exploitation → «Наш статус» connected → «Подключено»; без сопоставления: archiveRecord, complete, created, deleted, exploitationArchive, exploitationOut, exploitationTest, implement, implementStop, plan, quarantine, reserve, service, archivedLink. (Акутальная] Сфера.Конфигурации -5)
