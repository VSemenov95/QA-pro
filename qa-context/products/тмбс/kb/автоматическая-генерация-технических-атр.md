# Автоматическая генерация технических атрибутов по примеру события (кнопка «Добавить все атрибуты»)

> Кнопка «Добавить все атрибуты» на вкладке «Технические атрибуты» источника данных в статусе «Черновик» автоматически создаёт технические атрибуты по всем примитивным значениям загруженного примера события в JSON.

### Описание
- Пользовательская история: «Я как Администратор. Хочу иметь возможность автоматически сгенерировать технические атрибуты по примеру события. Для того, чтобы ускорить настройку источника данных и избежать ручного ввода большого количества атрибутов». Атрибуты формируются на основании загруженного примера события в формате JSON; функция доступна в Администрирование / Источники данных и применяется только к источникам в статусе «Черновик». (33-ТМ. Автоматическая генерация правил парсинга технических атрибутов в источнике данных)

[СА] Автоматическая генерация правил парсинга технических атрибутов в источнике данных», статус «На ревью». ### Экраны и навигация
- Администрирование\Источники данных → «Создать» (форма источника в статусе «Черновик», status = DRAFT) или выбор существующего (FE: GET /api/datasource/{dataSourceRowId}) → страница конфигурации, вкладка «Технические атрибуты»: список атрибутов (если есть) и кнопка «Добавить все атрибуты». Если на вкладке «Предварительная обработка» включена предварительная обработка JSON, FE отправляет POST /api/functions/splitMessage. После генерации атрибуты добавляются в список на вкладке. (33-ТМ. Автоматическая генерация правил парсинга технических атрибутов в источнике данных; 11-ТМ. [СА] Автоматическая генерация правил парсинга технических атрибутов в источнике данных)

### Поля и элементы
- Кнопка «Добавить все атрибуты»: для «Черновик» доступна; для другого статуса — disabled. Подсказка при наведении (для «Черновик»): «Из каждого массива будут добавлены только атрибуты из последнего элемента». Также кнопка «Сохранить»; иконка/подсказка с ошибкой у названия атрибута, нарушающего ограничения. Таблица атрибутов (13.1): поле name; название — null; тип — строка; макс. длина — 128; M/O, Default не заданы; правила валидации 1-7. (33-ТМ. Автоматическая генерация правил парсинга технических атрибутов в источнике данных; 11-ТМ. [СА] Автоматическая генерация правил парсинга технических атрибутов в источнике данных)

### Бизнес-правила и ограничения
- Доступность (проверяет FE): status = DRAFT и пример события загружен (messageTemplate not null). (11-ТМ. [СА] Автоматическая генерация правил парсинга технических атрибутов в источнике данных; 33-ТМ. Автоматическая генерация правил парсинга технических атрибутов в источнике данных)
- Алгоритм FE: 1) GET /api/functions/messageFunctions; 2) GET /api/teachnical-attribute/name-replacement-rules (в документе именно «teachnical»); 3) парсинг JSON примера, при ошибке выполнение прекращается; 4) рекурсивный обход, собираются полные JSON-пути примитивных значений (строка, число, boolean, null); из каждого массива — только последний элемент (индекс -1); 5) проверка дублей; 6) генерация названия по полному пути: правила замены + нормализация (таблица 1.1); 7) два списка: успешные (для добавления, «функция=, JSON-нода=» — значения не указаны) и не добавленные с причиной; 8) уведомление об успехе со списком добавленных; 9) добавление в список на вкладке; 10) при нарушении ограничений — подсказка с ошибкой; 11) изменения сохраняются только после «Сохранить». (11-ТМ. [СА] Автоматическая генерация правил парсинга технических атрибутов в источнике данных)
- Для примитива: функция getText; JSON-путь — полный путь до значения (для массивов с [-1]); JSON-нода #message; название — полный путь. Обходится вся структура, включая вложенные объекты. (33-ТМ. Автоматическая генерация правил парсинга технических атрибутов в источнике данных)
- Дубликаты: атрибуты с совпадающим JSON-путём (в СА — с функцией getText) не добавляются и не изменяются; параметры event_time без изменений. Если все уже добавлены — «Все атрибуты уже добавлены». (33-ТМ. Автоматическая генерация правил парсинга технических атрибутов в источнике данных; 11-ТМ. [СА] Автоматическая генерация правил парсинга технических атрибутов в источнике данных)
- Правила валидации имён (13.2 / 1.1): 1) Замена по списку: на верхнем уровне (единственное правило payload -> object), на любом уровне кроме верхнего (список пуст) — имя заменяется по конфигурации; 2) snake_case: только a-z и _, символы преобразуются; 3) нормализация: только a-z, 0-9, _, прочие удаляются; 4) первый символ — буква, иначе префикс attr_; 5) запрещённые имена (blacklist): «registry_id», «transaction_uuid», «uuid», «source_timestamp», «insert_timestamp», «merge_timestamp», «event_source_id», «event_stage», «event_transaction_type» — префикс attr_; 6) длина ≤ 128, иначе иконка с ошибкой; 7) пустое имя после обработки — иконка с ошибкой; 8) уникальность: имя существует — назначается {имя_атрибута}_n. (33-ТМ. Автоматическая генерация правил парсинга технических атрибутов в источнике данных; 11-ТМ. [СА] Автоматическая генерация правил парсинга технических атрибутов в источнике данных)
- Автозамена: на BE переменная окружения ATTR_NAME_REPLACEMENT_RULES (JSON), дефолт {"top-level-only":[{"from":"payload","to":"object"}],"after-top-level":[]}. top-level-only и after-top-level — обязательные массивы ReplacementRule (from, to — обязательные string, from — точное совпадение). Не задана/пуста — пустой массив; некорректный JSON — ошибка логируется, пустой массив. Уровень по числу сегментов JSON-пути: $.payload = 1 (верхний), $.payload.user = 2, $.payload.user.id = 3 (вложенные). Для атрибута правило применяется один раз; новые правила — только для новых генераций. (11-ТМ. [СА] Автоматическая генерация правил парсинга технических атрибутов в источнике данных)

### API и интеграции
- GET /api/datasource/{dataSourceRowId}; POST /api/functions/splitMessage; GET /api/functions/messageFunctions; GET /api/teachnical-attribute/name-replacement-rules — новый контракт «Получение правил замены имен технических атрибутов при автогенерации»; переменная BE ATTR_NAME_REPLACEMENT_RULES. (11-ТМ. [СА] Автоматическая генерация правил парсинга технических атрибутов в источнике данных)

### Сообщения и ошибки
- «Пример события отсутствует» — пример не загружен, генерация не выполняется. «Все атрибуты уже добавлены». Успех — уведомление со списком добавленных атрибутов. Нарушение ограничений — иконка/подсказка с ошибкой. Сохранение: «Источник данных успешно обновлен»; сбой: «Что-то пошло не так». (33-ТМ. Автоматическая генерация правил парсинга технических атрибутов в источнике данных)
- Некорректный JSON примера — генерация не выполняется (текст см. «Расхождения»). (33-ТМ. Автоматическая генерация правил парсинга технических атрибутов в источнике данных; 11-ТМ. [СА] Автоматическая генерация правил парсинга технических атрибутов в источнике данных)

### Роли и права
- Роль: Администратор; ролевая модель применяется для UI и API; таблица разрешений ID не заполнена. (33-ТМ. Автоматическая генерация правил парсинга технических атрибутов в источнике данных)
