## Назначение и границы
- ТМБС — система мониторинга бизнес-сервисов (БС): карточки мониторинга (КМ), контрольные точки (КТ), метрики, вычисляемые атрибуты (ВА), события мониторинга, источники данных, технические атрибуты, шаблоны, отправка отклонений/событий/метрик во внешние системы (ЗСМ, ОСУС/ЭКОС). Сведения взяты из описаний таблиц БД и технических решений (PDF), не из UI/API.
- Сфера.Конфигурации-5.pdf — версия на 15.06.2026 (ЦС, Сервисы, ИС).
- Продукт «Сфера: Транзакционный Мониторинг Бизнес-Сервисов»: объединяет события продуктов бизнес-сервиса в сквозную транзакцию, выявляет нарушения прохождения транзакции, контролирует качество БС; релиз PPBP-26.3.0-4; правообладатель ООО «ГК «Иннотех»; в ЕРРП запись №16981 от 21.03.2023, класс ПО 05.13 (Сфера.ТМБС_Описание_продукта_PPBP-26.3.0-4.pdf)
- Целевая аудитория: поддержка и эксплуатация, ИБ, владельцы БС, разработчики ПО (Описание продукта PPBP-26.3.0-4)

- КТ: checkpoint, checkpoint_group, group_rule, enrichment_rule, enrichment_rule_value, enrichment_constant, checkpoint_attribute, identifier, completeness_computed_attribute_checkpoint.
- Метрики: metric, metric_interval, metric_service (метрики Сервиса), dictionary_metric_unit.
- ВА: computed_attribute; типы «Общие» (general_computed_attribute) и «Полнота» (completeness_computed_attribute); general_computed_attribute_interval; computed_attribute_group_reference; dictionary_attribute_unit.
- Ручные события и коды отклонений: monitoring_event, code_deviation.
- Источники данных: data_source, data_source_inf_system, data_source_connector_kafka (коннектор «Астром»), data_source_data_collecting_info, data_source_connector_astrom_key. Внутри: технические атрибуты, конструктор правил парсинга, автогенерация (PPBP-1628), сохранение событий в ClickHouse.
- Интеграция со Сфера.Конфигурации: configuration_integration_is / _services / _chains / _link (в п.6.3.3 заголовок «_chain», в списке — _chains; уточнено: Сфера.Конфигурации-5.pdf), datablock и datablock_data (обновляются при загрузке цепочек); обновление по шедулеру админ-сервиса.
- Глобальные настройки отправки (admin_settings).
- Отправка метрик БС в ЗСМ (trmonbs-metrics-calculator-service, Kafka) (ТМ. [СА] Отправка метрики БС в ЗСМ-7).
- Передача событий мониторинга для устранения отклонений в ЗСМ/ОСУС через Kafka (2-Передача событий мониторинга…).
- Массовые операции над сущностями из шаблона (PPBP-2309): смена статуса, удаление, обновление по шаблону для ВА и метрик.
- Миграции БД: flyway_schema_history; flyway_admin_schema_history (admin-схема; installed_on INT4, назначение с «?»).
- Фича «Передача метрик из ТМБС в ЗСМ в привязке к сервисам с агрегирующим расчётом на стороне ТМБС» (PPBP-1742, PPBP-1863 ч2, PPBP-1906 — изменена логика репликации service; US PPBP-1799: список сервисов с поиском по наименованию/коду). Связанные документы: Сфера.Конфигурации, «Сервис — Пермиссии для Сервисов», «ТМ. [СА] Принадлежность метрик БС, выч. атрибутов и КТ к Сервису»; сиквенс-диаграммы «Список Сервисов» и «Карточка Сервиса» (ТМ. [СА] Список сервисов-10.pdf, ТМ. Просмотр списка сервисов-19.pdf)
- Группы функций (Описание продукта PPBP-26.3.0-4): 1 интеграция источников/коннекторы; 2 конфигурирование мониторинга и склейки (КМ, версии КМ, КТ, идентификаторы, источники, метрики и пороги, история изменений, применение в близком к реальному времени); 3 связка транзакций (сквозной идентификатор, несвязанные события); 4 хранение событий, поиск транзакций; 5 расчёт метрик/ВА, отклонения, события мониторинга; 6 передача событий во внешние продукты; 7 визуализация (дашборды БС, список/поиск/детализация транзакций)
- Конвейер обработки (7 этапов): приём → предобработка (дедупликация) → обогащение (распределение по БС) → склейка в транзакцию → расчёт характеристик транзакций → расчёт показателей БС → формирование событий мониторинга. Компоненты: gateway, FE, admin-service (API настройки мониторинга), config-service (доставка конфигураций), event-collector-kafka (забор из источников → Kafka ТМБС), preprocessor-service, enrichment-service, merging-transactions-service, online-metric-service (ВА), metric-calculator-service (метрики БС), metric-treshold-service (события для Зонтичной системы), ecm-integration-service. Хранилища: PostgreSQL (конфигурации), Scylla (сырые события для склейки), ClickHouse (транзакции, ВА, метрики), Redis (блокировки расчётов), Kafka (обмен между микросервисами). Внешний интерфейс — тонкий клиент «Настройка мониторинга» (Архитектура PPBP-26.3.0-4, табл. 2.3-1, 4-1)

## Роли и пользователи
- PPBP_ADMIN_SETTINGS_READ и PPBP_ADMIN_SETTINGS_UPDATE выдаются только при объекте доступа 'ALL_OBJECT' в ДИР (ТМ. [СА] Настройка отклонений).
- Для ручек массовых операций нужны разрешения: чтение бизнес-сервисов (Бизнес-сервис), удаление/обновление ВА (Вычисляемые атрибуты) и метрик (Метрика). Массовые операции доступны администратору ТМБС.
- Права смены статуса КТ: PPBP_CHECKPOINT_STATUS_CHANGE_FROM_<X>_TO_<Y> (напр. FROM_DRAFT_TO_CONNECTED, FROM_MONITORING_TO_DRAFT, FROM_DISCONNECTEDMANUAL_TO_CONNECTED) (25-Контрольная точка.pdf).
- Права смены статуса источника данных: PPBP_DATASOURCE_STATUS_CHANGE_FROM_<X>_TO_<Y>; Авария→Подключен — PPBP_DATASOURCE_STATUS_INCIDENT_TO_CONNECTED, Авария→Отключен — PPBP_DATASOURCE_STATUS_INCIDENT_TO_DISCONNECTED (Источник данных-10.pdf).
- Тестовые роли на стендах: «Администратор», «Просмотровая роль», «Аудитор ИБ», «Владелец БС», «Технолог БС» (30-ТМ.Онбординг.pdf).
- Роли по описанию продукта: «Администратор системы мониторинга» (настройка конфигурации мониторинга БС, создание/редактирование объектов, визуализации БС/атрибутов/метрик); «Владелец БС» (просмотр визуализаций, отклонений, показателей качества БС); «Аудитор ИБ» (аудит данных продукта). Доступ на просмотр/редактирование настраивается на уровне основных объектов и их атрибутов (Описание продукта PPBP-26.3.0-4)
- Роли (Архитектура, табл. 11.1-1): «Технолог БС» — ставит БС на мониторинг, настраивает ВА и метрики, просматривает визуализации; «Просмотровая роль» — просмотр объектов продукта; служебные роли и технологические учётные записи (табл. 11.2-1, 11.3-1) не заполнены.
- PPBP_SERVICE_READ (GET /api/service/header, страница «Сервисы») и PPBP_SERVICE_UPDATE (POST /api/service/update-config/{serviceId}): единственная роль — Администратор (Роль 1); проверки на BE и FE, в UI и API; без разрешения — 403. Неоднозначность: в ТЗ для FE указана PPBP_SERVICE_READ, а создаётся PPBP_SERVICE_UPDATE; в п.4.2 для POST указана проверка PPBP_SERVICE_READ и GET /api/service/header — вероятная опечатка (ТМ. [СА] Список сервисов-10.pdf, ТМ. Просмотр списка сервисов-19.pdf)

## Экраны и навигация
- Панель администрирования «Настройка отклонений»: режим обслуживания через КМ. В форме ручного события: тоггл «Отправлять отклонения» (активен при deviation=true в GET /api/monitoring-event/{eventId}; PUT/POST передают deviation: true) и селект «Код отклонений» (из GET /api/code-deviation/).
- Форма ручного события: селект «Группа оповещений» → customAttributes.ppbpNotificationGroup (не выбрана — пустая строка; в БД monitoring_event.notification_group_name); для транзакций 4 поля селектом: TransactionId, массивы FinancialInstructionIds и FinancialTransactionIds; DashboardUrl = ссылка + TransactionId.
- Карточка шаблона, вкладка «Бизнес-сервисы»: сущности отмечаются галочками для массовых операций; только для шаблона в статусе «Активный». В обновлении по шаблону есть флаг «Синхронизировать пороги критичности».
- «Источники данных» → выбор источника → кнопка «Настроить» в шапке → шторка сохранения событий: чекбоксы «Сохранять JSON целиком» и «Сохранять технические атрибуты по отдельности»; поля «Срок хранения данных» и «Версия» (активны, только если включён хотя бы один чекбокс); кнопки «Применить» (PUT /api/datasource-data-collecting/{dataSourceId}) и «Закрыть». Оба чекбокса выключены — сохранение событий отключено (PPBP-1630).
- Страница «Создание/редактирования технического атрибута» (из раздела «Технические атрибуты» источника): конструктор функций с вложенностью «родительская — дочерняя функция», блок «Пример события», кнопка «Проверить код» у функции, кнопка «Сохранить». После сохранения закрывается и открывается «Создание источника данных» → «Технические атрибуты» с новым атрибутом (PPBP-1629).
- Автогенерация тех. атрибутов (PPBP-1628): Администрирование\Источники данных → «Создать» (статус «Черновик», DRAFT) или выбор существующего (GET /api/datasource/{dataSourceRowId}) → вкладка «Технические атрибуты» → «Добавить все атрибуты». Доступна только если источник в DRAFT и загружен пример события (messageTemplate not null). Если на вкладке «Предварительная обработка» включена предобработка JSON — FE вызывает POST /api/functions/splitMessage. После генерации — уведомление об успехе со списком добавленных атрибутов; у нарушающих ограничения — иконка/подсказка с ошибкой; сохранение только по кнопке «Сохранить» (11-ТМ…правил парсинга).
- Карточка Сервиса: кнопка «Обновить карточку» переводит метрики Сервиса из «Подключено» в «На мониторинге» (5-Метрика Сервиса.pdf).
- КМ: функции «Поставить на мониторинг» и «Снять с мониторинга» автоматически меняют статусы КТ (25-Контрольная точка.pdf), ВА и метрик.
- Поля «Имя контрольной точки» / «Имя вычисляемого атрибута» / «Имя метрики» (ввод, обязательные, редактируемые, уникальны в рамках КМ): по умолчанию «Новая контрольная точка» / «Новый вычисляемый атрибут» / «Новая метрика»; ошибки «Контрольная точка с таким именем уже существует в карточке мониторинга» / «Вычисляемый атрибут с таким именем уже существует в карточке мониторинга» / «Метрика с таким именем уже существует в карточке мониторинга» (4-ТМ.06.03, 4-ТМ.06.05, 4-ТМ.06.06).
- ВА: настраивается функция «дополнительные поля в вычисляемых атрибутах» — выбранные тех. атрибуты добавляются столбцами в ClickHouse-таблицу атрибутов БС (8-bs_{$bs}_attribute.pdf).
- Ошибки валидации тех. атрибута: под полем ввода (нельзя закрыть) — при вводе недопустимых символов; всплывающее окно справа снизу (исчезает по таймауту, можно закрыть) — при сохранении источника (тексты в «Бизнес-правила»). Некорректное название источника: текста ошибки нет, блокируется кнопка сохранения названия (7-ТМ.Валидация источника данных).
- Главная: «Быстрые ссылки» → кнопка «Сервисы» (title «Сервисы», body «Просмотр и конфигурирование настроек Сервисов»), видна авторизованному в SFERA с Ролью 1 (Администратор). Также пункт верхнего меню «Сервисы» (при PPBP_SERVICE_READ), маркируется в т.ч. при наведении на страницах «Бизнес-сервисы», «Карточки мониторинга», «Источник данных», «События источника данных» и дочерних (ТМ. Просмотр списка сервисов-19.pdf)
- Страница «Сервисы»: «Поиск» (плейсхолдер «Поиск по ID, коду, Сервису, Бизнес Сервису»; крестик сбрасывает), таблица ID, Код, Название Сервиса, ID Внешний, Бизнес Сервисы (id int32, остальные string), пагинация «Записей на странице» (10, 20, 50), «Вперед»/«Назад». Нет результатов — «Ничего не найдено. Уточните поисковый запрос». Колонка БС: 2 чипса (до 20 символов), при >2 БС — count-чипс (при наведении список). При 400/403/404/500 или 200 без данных — пустая таблица с поиском и пагинацией; макеты ошибок отложены (ТМ. Просмотр списка сервисов-19.pdf, ТМ. [СА] Список сервисов-10.pdf)

## API и интеграции
- Флаги send_deviation / send_monitoring_events / send_metric управляют отправкой (глобально в admin_settings и в monitoring_card).

- Коды отклонения: GET/POST /api/code-deviation/, PATCH/DELETE /api/code-deviation/{codeDeviationId}.

## Бизнес-правила и ограничения
- Интеграция со Сфера.Конфигурации только дополняет связи БС с ИС (bs_system_inf_system): существующие связи удалять нельзя, новые добавляются (Сфера.Конфигурации-5.pdf).
- Цепочка сервисов (serviceChain) обрабатывается как БС и наследует ИС всех сервисов цепочки через bs_system_inf_system; при добавлении ИС к сервису она появляется у БС цепочки. Прочие сервисы (ITService/Service) хранятся в service только для обогащения связей и не ставятся на мониторинг как БС (Сфера.Конфигурации-5.pdf).
- Обновление интеграционных таблиц выполняется только по расписанию шедулера админ-сервиса, 1 раз в сутки; вне расписания таблицы не обновляются; обновляются только объекты с разрешёнными статусами (Сфера.Конфигурации-5.pdf).
- Связи из configuration_integration_link обрабатываются только с relationType.relationKey = PARENT; связи с иным relationKey не попадают в s_system_bs_system, s_system_inf_system, bs_system_inf_system. При БС→Сервис и Сервис→ИС без совпадения CI2 с external_id запись не создаётся и обработка завершается (Сфера.Конфигурации-5.pdf).
- bs_system_inf_system заполняется так: по external_id = CI1 находится внутренний ID БС, через s_system_bs_system определяется service_id, через s_system_inf_system — inf_system_id; формируются записи (inf_system_id, bs_id) (Сфера.Конфигурации-5.pdf).
